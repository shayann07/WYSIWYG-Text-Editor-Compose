# Windows native keyboard / IME qualification fixtures

These are private Windows/JDK 23 test tools. They do not install language components or change input-language defaults. Actual keyboard actions use the supported computer-use runtime against the uniquely identified owned fixture. No test API injects text or composition callbacks.

`OwnedKeyboardLayout.java` reads loaded/current/default HKLs through existing Windows APIs. Activation is restricted to the named Urdu/Japanese qualification layouts and refuses unless its own process owns keyboard focus. It captures the original context, verifies the default input language, restores the original layout and attempts to unload introduced handles. `LoadKeyboardLayout` is system-wide on Windows 8+; this is not described as a process-local operation. Every live result must verify cleanup and the user preload/substitute configuration. Do not force-remove user layouts or repair the unrelated unregistered profile entry found during inspection.

The ordinary integrated verifier runs only `verify_capability.py`: it compiles the helper, queries native state and proves an activation request without an owned foreground window refuses without mutation. It does not replay GUI input. Non-Windows or missing existing JDK 23+ tooling is NOT RUN. GUI fixtures take a new output directory and the compiled helper on their classpath, using `--native-keyboard-probe --keyboard-output=<directory>`. These internal flags are not general library APIs or default application behavior. `--native-reference` adds a disposable standard Swing document for comparison, never a mirror of the editor's canonical document.

## Executed Urdu keyboard smoke

`native-keyboard-live-20261018-0747` records real physical K/U/J/I input through the Microsoft Urdu layout, producing exact U+06A9/U+062A/U+0627/U+0628 (`کتاب`). It then records physical English keys, a native bidi-boundary round trip, whole mixed-script selection and bold-format Undo/Redo shortcuts. Eight KEY_TYPED events and zero IME text events were observed; no Paste/type_text route was used. Visual native captures were inspected. This is native plain-keyboard evidence, not IME candidate or complete U1/U2 qualification.

`check_urdu_evidence.py` audits the saved trace/diagnostics/restoration/config artifacts and the actual historical build identities. It checks relevant current product sources still match that observed build, while allowing later test tooling to differ. The audit never claims to rerun the GUI on a newer build. Before/after loaded/default/current state returned to US English, the introduced Urdu handle unloaded, and preload/substitute settings matched. The document was cleaned and the owned JVM exited normally. Computer use was reset immediately after the bounded checks.

JVM locale diagnostics remained en_US during real Urdu input while the native GUI HKL was Urdu. Do not treat that field or an earlier JVM locale-selector refusal as an exhaustive OS capability test. Internal `nativeQualified=false` still records the unqualified context-retirement/fence scope and is not overwritten by this keyboard smoke.

The initial diagnostic used MapVirtualKeyEx's VK-to-character mode, which returns Latin A–Z for those virtual keys regardless of layout. It was not used as the word oracle. The updated helper uses ToUnicodeEx with its Windows 10+ no-state-change flag; this mapping query itself is not real input or an IME conversion test.

## Japanese follow-up remains open

The Japanese keyboard and the registered Microsoft IME component exist on this machine. The registered COM server is `System32/IME/IMEJP/imjptip.dll`; initial probes of other common paths were not sufficient to establish absence. A basic Japanese HKL activation plus the documented input-mode toggle yielded Latin text and no composition callbacks. A separate standard JTextArea under the same activation path also yielded Latin text and zero IME callbacks. This does not prove the custom surface is defective or that the installed IME is unavailable.

Both native Japanese fixtures restored US input/default state and unloaded their introduced handle. The comparison control is deliberately separate and never changes the editor document. Next inspect the active full TSF input-processor profile and, if needed, qualify a temporary activation with prior-profile restoration; do not infer Microsoft IME activation from the numeric keyboard HKL alone. Do not install components, alter defaults or substitute injected composition events. Real candidate selection, native focus/recovery and retirement fencing remain unqualified until observed.

## Executed TSF follow-up

`TsfProfileProbe.java` queries the installed COM service through the SDK ABI. The current profile was an active/enabled US keyboard (type 2); Japanese was a text-service profile (type 1). GetProfile summary flags were zero and the machine-default Enable value was zero, but the explicit IsEnabledLanguageProfile call succeeded and returned true. Neither the summary flags nor the machine-default registry value can be treated as the current user's enabled-state oracle. The modern user-language list also contains Japanese's full CLSID/profile pair. The numeric preload entry `00002000` corresponds to the English (Pakistan) configuration in that modern list; lack of a matching legacy layout key is not a reason to repair it.

The owned fixture gained opt-in `tsf-query` and `prepare-ime` controls. They require the owned foreground PID, a captured original full profile and the prepared Japanese context. Activation uses FORPROCESS only, without enabling/disabling/registration/default-setting methods. Prior profile identity, language and physical layout are restored before the introduced handle is unloaded. Calling-thread COM/TSF resources have explicit lifetimes.

Two bounded live experiments did **not** qualify Japanese input. A process activation returned S_OK while subsequent main/EDT queries stayed on English and a native key remained Latin; the helper reported ProfileChangeNotVerified. A registered calling-thread TSF manager then allowed an explicit current-language step, but switching to Japanese returned E_FAIL. It stopped before claiming activation. Switching back to the captured English language/profile succeeded, and loaded/current/default input state returned to US English. All fixtures exited normally and the controller was reset.

These APIs and their setup are experimental, not the production input adapter. Current observations are specific to the calling Java threads; they do not prove the state of the native AWT window thread or an OS-profile selection made through the normal input UI. Do not repeat the same activation loop or infer the editor is defective. Next native work needs a supported way to select/observe the full profile in the actual GUI/input context, with verified restoration; otherwise retain NOT QUALIFIED and work on independent M1 gates. CLI/read-only checks never call these mutation paths. Service initialization is checked against captured input state, rather than assumed inert.

Primary TSF references: [GetActiveProfile](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfinputprocessorprofilemgr-getactiveprofile), [IsEnabledLanguageProfile](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfinputprocessorprofiles-isenabledlanguageprofile), [ActivateProfile](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfinputprocessorprofilemgr-activateprofile), and [ChangeCurrentLanguage](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfinputprocessorprofiles-changecurrentlanguage). The ABI declarations came from Microsoft's win32metadata WinSDK header; no SDK installation or C++ toolchain was needed.
